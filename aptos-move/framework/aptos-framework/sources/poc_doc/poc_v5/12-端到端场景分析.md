# 12 — 端到端场景分析

本文档通过完整的场景走查，串联所有模块的交互逻辑，帮助理解 PoC 共识系统的实际运行过程。

## 12.1 场景一：验证者从零上线

### 前置条件

- 链已完成创世，至少有一个活跃验证者
- 新验证者 `ValB`（owner = operator = `0xBBBB`）
- 链下 Operator 已为 `ValB` 计算了算力

### 完整流程

```mermaid
sequenceDiagram
    participant OP as 链下 Operator
    participant PS as PowerStore
    participant ValB as 验证者 ValB
    participant SR as StakingRegistry
    participant ST as Stake

    Note over OP,ST: === 第一步：算力上传 ===
    OP->>PS: stage_batch_update(period+1, [0xBBBB], [10000])
    Note over PS: ValB 的算力 = 10000（下个 period 生效）

    Note over OP,ST: === 等待 period 边界 ===
    Note over ST: on_new_epoch() → commit_next_period_if_boundary()
    Note over PS: current_period += 1，ValB 算力生效

    Note over OP,ST: === 第二步：初始化 StakePool ===
    ValB->>ST: initialize_stake_owner(0, 0xBBBB)
    Note over ST: 创建 StakePool + OwnerCapability<br/>自动注册到 staking_registry

    Note over OP,ST: === 第三步：存款 ===
    ValB->>SR: deposit(1_000_000_000)
    Note over SR: deposit = 1B octas = 10 TOPO<br/>deposit_cover = 1B / 100K = 10000

    Note over OP,ST: === 第四步：自委托 ===
    ValB->>SR: delegate(0xBBBB)
    SR->>PS: get_user_committed_power(0xBBBB)
    PS-->>SR: 10000
    SR->>SR: effective_power = min(10000, 10000) = 10000
    SR->>SR: 10000 >= 1 (min_active_power) ✓
    Note over SR: ValB 加入自己的 delegator_list

    Note over OP,ST: === 第五步：设置共识密钥 ===
    ValB->>ST: rotate_consensus_key(0xBBBB, pubkey, pop)
    ValB->>ST: update_network_and_fullnode_addresses(0xBBBB, net, fullnode)

    Note over OP,ST: === 第六步：加入验证者集合 ===
    ValB->>ST: join_validator_set(0xBBBB)
    ST->>SR: get_validator_joining_power(0xBBBB)
    SR-->>ST: 10000（owner 自身算力）
    ST->>SR: get_validator_total_power(0xBBBB)
    SR-->>ST: 10000
    ST->>ST: 10000 >= minimum_stake ✓
    ST->>ST: 10000 <= maximum_stake ✓
    Note over ST: 加入 pending_active 队列

    Note over OP,ST: === 下个 Epoch ===
    ST->>ST: on_new_epoch()
    Note over ST: pending_active → ACTIVE<br/>ValB 正式成为活跃验证者
```

## 12.2 场景二：用户质押并赚取奖励

### 前置条件

- 验证者 `ValA` 已活跃，commission = 10%（1000 bps）
- 用户 `Alice`（`0xAAAA`）有 5 TOPO
- 链下 Operator 已为 Alice 上传算力 = 800

```mermaid
sequenceDiagram
    participant A as Alice
    participant SR as StakingRegistry
    participant PS as PowerStore
    participant ST as Stake

    Note over A,ST: === 存款 ===
    A->>SR: deposit(500_000_000)
    Note over SR: Alice.deposit = 5 TOPO = 500M octas<br/>deposit_cover = 500M / 100K = 5000

    Note over A,ST: === 委托 ===
    A->>SR: delegate(ValA)
    SR->>PS: get_user_committed_power(Alice)
    PS-->>SR: 800
    SR->>SR: effective_power = min(800, 5000) = 800
    Note over SR: 算力是瓶颈，质押有余量

    Note over A,ST: === Epoch N 结束 ===
    ST->>SR: distribute_epoch_rewards(ValA, 95, 100, rate, denom)

    Note over SR: ValA 的 delegator_list:<br/>  ValA_owner: power=10000<br/>  Alice: power=800<br/>pool_power = 10800

    Note over SR: epoch_reward = 10800 × rate × 95 / (denom × 100)
    Note over SR: commission = reward × 10% = ...
    Note over SR: Alice_share = distributable × 800 / 10800

    SR->>SR: mint Alice_share → Alice.deposit
    Note over SR: Alice.deposit 增长<br/>deposit_cover 也随之增长

    Note over A,ST: === Epoch N+1 ===
    Note over SR: Alice.deposit 更大了<br/>但 committed_power 仍是瓶颈<br/>effective_power 仍 = 800（或衰减后更低）
```

### 奖励复利效应数值走查

```
假设：
  rewards_rate = 1, rewards_rate_denominator = 1000
  ValA pool_power = 10800, commission = 10%
  Alice power = 800, 成功提案率 = 95%

Epoch N:
  epoch_reward = 10800 × 1 × 95 / (1000 × 100) = 10 (截断)
  commission = 10 × 1000 / 10000 = 1
  distributable = 10 - 1 = 9
  Alice_reward = 9 × 800 / 10800 = 0 (截断，太小)

  → 实际场景中 rewards_rate 会更大，这里简化演示

假设更大的 pool 和 rate:
  pool_power = 1,000,000, Alice power = 80,000
  rewards_rate = 100, denominator = 10000
  成功率 = 100%

  epoch_reward = 1,000,000 × 100 / 10000 = 10,000
  commission = 10,000 × 10% = 1,000
  distributable = 9,000
  Alice_reward = 9,000 × 80,000 / 1,000,000 = 720

  Alice.deposit += 720 octas
  新 deposit_cover = (原 deposit + 720) / 100,000
```

## 12.3 场景三：算力衰减与强制退出

```mermaid
sequenceDiagram
    participant OP as 链下 Operator
    participant PS as PowerStore
    participant SR as StakingRegistry
    participant ST as Stake
    participant Bob as Bob

    Note over OP,ST: === 初始状态 ===
    Note over Bob: committed_power = 100<br/>deposit = 20M octas<br/>deposit_cover = 200<br/>effective_power = 100<br/>min_active_power = 100

    Note over OP,ST: === Period 1：Operator 未更新 Bob 的算力 ===
    ST->>PS: commit_next_period_if_boundary()
    Note over PS: current_period = 1

    ST->>SR: force_undelegate_below_threshold(validator)
    SR->>PS: get_user_committed_power(Bob)
    PS-->>SR: 100 × 0.995 = 99（衰减后）
    SR->>SR: effective_power = min(99, 200) = 99
    SR->>SR: maintain_threshold = ⌈100 × 8000 / 10000⌉ = 80
    SR->>SR: 99 >= 80 → 不退出

    Note over OP,ST: === Period 2~40：持续未更新，缓慢衰减 ===
    Note over PS: 每个 period 衰减 0.5%

    Note over OP,ST: === Period 45：算力降至阈值以下 ===
    ST->>PS: commit_next_period_if_boundary()
    Note over PS: current_period = 45

    ST->>SR: force_undelegate_below_threshold(validator)
    SR->>PS: get_user_committed_power(Bob)
    PS-->>SR: 100 × 0.995^45 ≈ 79（继续衰减）
    SR->>SR: effective_power = min(79, 200) = 79
    SR->>SR: 79 < 80 → 强制退出！

    SR->>SR: 从 delegator_list 移除 Bob
    SR->>SR: Bob.delegated_to = 0x0
    SR->>SR: Bob.cooldown_until_secs = now + 30天

    Note over Bob: Bob 进入冷却期<br/>不再参与奖励分配
```

### 衰减时间线

```
min_active_power = 100, force_exit_power_bps = 8000
maintain_threshold = 80, retention = 99.5%

Period 0:  power = 100  → effective = 100 ✓ (>= 80)
Period 1:  power = 99   → effective = 99  ✓
Period 10: power = 95   → effective = 95  ✓
Period 44: power = 80   → effective = 80  ✓ (刚好)
Period 45: power = 79   → effective = 79  ✗ (< 80, 强制退出)
```

## 12.5 场景五：验证者佣金调整与委托者影响

```
假设：
  ValA commission 从 10% 调整为 20%
  pool_power = 100,000
  epoch_reward = 1,000

调整前（commission = 10%）：
  commission = 1,000 × 10% = 100
  distributable = 900
  委托者按算力比例分 900

调整后（commission = 20%）：
  commission = 1,000 × 20% = 200
  distributable = 800
  委托者按算力比例分 800

影响：
  - 验证者 owner 收入增加（200 vs 100 佣金 + 自身算力份额）
  - 委托者收入减少（分配池从 900 降到 800）
  - 委托者可能选择解委托，转投其他验证者
```

### 数值走查

```
初始：
  committed_power = 500
  deposit = 50,000,000 octas (0.5 TOPO)
  octas_per_power = 100,000
  deposit_cover = 500
  effective_power = min(500, 500) = 500

经过 10 个 epoch（假设每 epoch 奖励 100 octas）：
  deposit = 50,000,000 + 1,000 = 50,001,000
  deposit_cover = 50,001,000 / 100,000 = 500（整数截断，变化微小）

经过 1 个 period（算力衰减 0.5%，无新上传）：
  committed_power = 500 × 0.995 = 497
  effective_power = min(400, 500) = 400
  → 算力衰减导致有效算力下降

Operator 上传新算力 = 600：
  committed_power = 600（下个 period 生效）
  effective_power = min(600, 500) = 500
  → 质押成为瓶颈，需要追加存款才能完全利用算力

追加 deposit(10,000,000)：
  deposit = 60,001,000
  deposit_cover = 600
  effective_power = min(600, 600) = 600
  → 均衡状态

解委托后提取：
  withdraw_deposit() → 获得 60,001,000 octas
  → 比初始投入多了 10,001,000（奖励部分）
  → 实际收益 = 累积奖励 - 追加存款的机会成本
```

## 12.8 关键时序约束总结

```mermaid
graph TB
    subgraph "Epoch 内时序"
        T1["区块生产<br/>record_fee() 累积交易费"]
        T2["update_performance_statistics()<br/>记录提案成功/失败"]
    end

    subgraph "Epoch 边界时序（严格顺序）"
        E1["1. 奖励结算<br/>使用旧 period 算力"]
        E2["2. Period 推进<br/>current_period += 1"]
        E3["3. 强制退出<br/>使用新 period 算力"]
        E4["4. 状态转换<br/>pending → active/inactive"]
        E5["5. 集合重建<br/>过滤 < minimum_stake"]
    end

    subgraph "用户操作时序"
        U1["deposit → delegate<br/>（需要先有算力和存款）"]
        U2["undelegate → 冷却期 → withdraw<br/>（严格顺序）"]
    end

    T1 --> E1
    T2 --> E1
    E1 --> E2 --> E3 --> E4 --> E5
```

**为什么奖励在 period 推进之前分配**：
- 公平性：用户在旧 period 的贡献应该按旧 period 的算力获得奖励
- 如果先推进 period，算力衰减后再分配，用户会少得奖励

**为什么强制退出在 period 推进之后执行**：
- 及时性：新 period 的算力衰减应该立即反映在退出检查中
- 如果用旧 period 检查，已经衰减的用户会多留一个 epoch
