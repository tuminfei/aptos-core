# PoC 节点 smoke 测试

对应 [核心测试用例](../../../../docs/draft/POC_CORE_TEST_CASES.md) 中需要真实节点、签名交易和跨节点状态证据的场景。所有测试名称包含 `poc_`，统一从仓库根目录运行：

```bash
cargo build --profile ci -p aptos-node --features failpoints,smoke-test
RUST_MIN_STACK=167772160 SMOKE_TEST_BIN_DIR="$PWD/target/ci" \
  cargo test --profile ci -p smoke-test --lib \
  --features aptos-config/failpoints poc_ -- --test-threads=1 --nocapture
```

本地可将构建和测试都改为默认 dev profile，并将二进制目录改为 `$PWD/target/debug`；执行记录必须注明实际 profile 和节点摘要。用 `-- --list` 核对过滤器，仅列出测试不能计为运行通过。

当前目录共包含 75 项 `poc_` smoke 测试，所有新增场景最多启动 7 个节点；每项是否通过仍以对应源码、节点二进制和 bundle 的当次执行记录为准。

长期奖励 churn 用例按规模单独运行，避免把 ignored soak 与其他长测混在同一进程：

```bash
export RUST_MIN_STACK=167772160
export SMOKE_TEST_BIN_DIR="$PWD/target/ci"

# 普通回归；10 Epoch 档也包含在上面的 poc_ 全量命令中
cargo test --profile ci -p smoke-test --lib --features aptos-config/failpoints \
  poc::reward_churn::poc_reward_churn_10_epochs_exact -- --exact --test-threads=1 --nocapture

# nightly：100 Epoch 档
cargo test --profile ci -p smoke-test --lib --features aptos-config/failpoints \
  poc::reward_churn::poc_reward_churn_100_epochs_seeded -- --ignored --exact --test-threads=1 --nocapture

# 候选版本或奖励逻辑改动后的专用作业：1000 Epoch soak
cargo test --profile ci -p smoke-test --lib --features aptos-config/failpoints \
  poc::reward_churn::poc_reward_churn_1000_epochs_soak -- --ignored --exact --test-threads=1 --nocapture
```

T2/T2-F 显式恢复 `SwarmBuilder` 底层改写的原生测试创世参数。T2-F 仅缩短 Epoch 为 10 秒。首轮 Chunky 初始化单独计时，不计入停机观察或恢复换届预算。跨节点资源固定同一 `ledger_version`；失败交易允许正常收取 gas、更新序列号和发出费用事件。

`transactions.rs` 上传输入矩阵中的 32 名新用户批次使用 100 Octa/gas、最多 2,000,000 gas，上传钱包注资 10 TOPO；该文件的其余交易使用 1 Octa/gas。各生命周期变体单独记录 gas 配置和实际费用，供复现存储费预算；这些功能验证不作为 SYS-06 性能验收。

生命周期变体使用 1 小时 Epoch，通过授权治理交易推进；除冻结测试开启普通 DKG 外，两个 DKG 均关闭。算力生命周期保留 9995/3000；分配生命周期使用 10000/0；奖励占比生命周期使用 10000、初始占比 3000。这些配置均不是严格 T2。执行循环从同一版本的链上 `Configuration.epoch` 读取当前 Epoch，逐笔验证 `v-1 → v` 恰好推进一期。

固定周期用例保持 60 Epoch 到 121，四池始终保留 1 OHMP 原始版本及完整 units，逐期按旧期独立计奖基数和真实提案统计核对原生/PoC 收益；61/121 各只发出一次周期提交事件，原始版本和持仓物理表项没有换届写入。另一个用例从普通账户及真实治理脚本重放 `set_genesis_committed_power`：分别精确拒绝于 `system_addresses/0x50003` 和 `chain_status/0x30001`，治理脚本先排期的奖励占比随事务回滚；合法普通上传仍可恢复成功。

退出池历史用例保留 9995/3000：用户 E61 生效后，在 E62/E63 形成两个成熟变化及各一个检查点引用；E64 池退出委员会，至 E71 用户及原始版本均不访问，物理表项不主动推进。P7 上传结算两段历史并淘汰 P1，P9 明确零版本再淘汰 P2，零算力于 E77 生效；E79 两次只读查询、精确领取及重复领取 0。逐期独立计算旧期通胀、分流、池指数和持仓小数，退出后基数与新增奖励为 0，领取仅推进该池到已安装 Epoch；三个在任节点在同版本核对引用释放和金库。

上传容量用例采用 Open/最低4人/容量6、25%增长、保留比例5000、支持周期24、初始原始算力2^32、每池100 Octa保证金、最低10/最大1000 power、原生占比0和费用限额0。先公开清空并退出目标池，保留四个真实背景验证者；60→1 周期到 E82，再改为2且保留 B83，使 E83/P23 的下一期 E84 与边界 B85 分开。I24=2^40 时，批次 [u64::MAX,2] 的前项 units=2^120−2^56、后项=2^57，仅 B85 合计超限，精确拒绝 `poc_accounting/0x20008`。重试 [u64::MAX,1] 后，E83 未来、E84 下一期、E85 当前均恰好 2^120；公开回加目标池的聚合原始 power=2^64，被保证金在宽域限为100，确认回加节点在 E85 实际成功提案后，五节点同版本比较并继续提交。原始算力极限是合法公开输入，账户余额及奖励均未注入极限值。该用例停在 P24，不尝试不支持的 P25。

同文件的第二项容量用例在 E82 上传 `u64::MAX−255`、`u64::MAX−255` 和 512，使 E83 的当前、E84 和 B88 均为 `C=2^120`。当前满额时，owner 的同一分配请求会令 E84 变为 `C+2^64`，精确拒绝于 `poc_accounting/0x20008`，并核对版本、持仓、引用、事件、gas 和序列号；原目标仍可提交。释放第三名用户后原请求成功，E85 当前仍恰好为 C。随后以 5000→2500 覆盖两段大旧链，最终 E86 为 `C−3H/4`、B88 为 `C−H/2`，完整替换不会因中间撤销/重建值过大而误拒；引用为 1/2/1/1，目标节点实际提案后五节点同版本一致。合法公开写入不能构造 `current>C`，该损坏状态仍由隔离测试验证；本夹具整数通胀为零，不作为正收益检查点证据。
